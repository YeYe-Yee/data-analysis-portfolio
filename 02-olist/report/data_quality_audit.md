## 0. 结论先行

**数据可用。**&#8203; 10 项校验全部通过，4 张事实表中的关联关系无断链；共识别 **19 项数据质量问题**，其中 9 项已在导入/建模阶段修复或规避（D-15~D-19 为分析阶段新增），9 项需在分析阶段通过口径约定规避，1 项接受（D-04）。

进入建模前必须遵守的三条铁律：

1. **复购/留存一律用 `customer_unique_id`**，`customer_id` 是"一次下单身份"不是"人"。
2. **任何订单级指标先 `GROUP BY order_id` 再聚合**，`order_items` 天然是 1.142 行/单。
3. **"送达延迟"分析样本 = `order_status='delivered' AND order_delivered_customer_date IS NOT NULL`，n = 96,470。**&#8203;
4. **复购必须剔除同日多单**（`gap_to_second >= 1 天`），否则复购率虚高 30%（2.91% vs 2.05%）。

## 3. 逐项明细

### D-01 CRLF 换行符污染（已修复）

**现象**：9 个文件中有 2 个为 CRLF 行尾（`olist_order_reviews_dataset.csv`、`product_category_name_translation.csv`），其余 7 个为 LF。`reviews` 文件 104,720 物理行对应 99,224 条记录——评论正文内含约 5,496 个换行。

**影响**：`LINES TERMINATED BY '\n'` 会在每行末尾残留 `\r`。末列为文本时污值被静默写入（`category_translation` 检出 70/71 = 98.6% 脏行）；末列为 DATETIME 时 MySQL 仅告警并丢弃。

**处置**：`category_translation` 改用 `LINES TERMINATED BY '\r\n'` 重导，脏值归零。`reviews` 末列为 DATETIME，`\r` 被解析器丢弃，数据正确。

**教训**：`LOAD DATA` 必须显式声明行终止符，并在导入前用 `file`/字节扫描确认源文件换行格式；`OPTIONALLY ENCLOSED BY '"'` 不可省略，否则评论内换行会导致记录切分错误。

### D-02 重复导入 3 次（已修复）

**现象**：首次校验 `order_reviews` = 297,669 = 99,223 × 3，分毫不差。

**根因**：`order_reviews` 因 `review_id` 不唯一而未设主键，重复执行 `LOAD DATA` 时 MySQL 不做任何拦截。多轮调试中"报出大量警告但实际成功"的执行共 3 次。

**影响**：差评率等比率指标数值不变，但所有基于行数的统计（样本量、JOIN 结果集）全部 ×3。

**处置**：`TRUNCATE` 后重导，现 99,223 行。

**教训**：**警告 ≠ 失败**；无主键表的导入必须绑定 `TRUNCATE`，保证幂等。

### D-03 review_id 不唯一（口径规避）

99,223 行中仅 98,409 个不同 `review_id`，重复 814 行（0.82%）。该重复存在于原始数据中，非导入造成（重导后数字稳定复现）。

**处置**：`order_reviews` 不设主键；与 `orders` JOIN 前按 `order_id` 取最新一条（`MAX(review_creation_date)`）或先去重，否则订单数会虚增。

### D-04 少导入 1 行（接受）

源文件 99,224 条记录，实际入库 99,223 条，缺失率 0.001%。推测为某行因引号/反斜杠转义导致记录合并，未定位。**判定：不影响任何结论，记录在案。**&#8203;

### D-05 geolocation 境外坐标（已修复）

原始 `geolocation` 经纬度范围 lat −36.61~45.07、lng −101.47~121.11，远超巴西外接矩形（lat −33.75~5.27、lng −73.99~−34.79）。越界 **42 行（0.004%）**&#8203;。

抽样显示州名均为巴西州（AL/RJ/PA/PR），坐标却落在意大利（45.07°N/9.34°E ≈ 米兰）、西班牙（43.68°N/−7.41°E ≈ 加利西亚）、墨西哥等地。**成因：地理编码把巴西地名匹配到欧洲同名小镇**（Pau d'Arco、Portela 在葡/西/意均有同名地）。

已排除整列 lat/lng 互换：`ABS(lat) > 90` 行数为 0。

**处置**：按 bbox 过滤后聚合，坐标范围收敛为 lat −33.69~4.48、lng −72.92~−34.80，全部落在巴西境内。同时剔除 42 行（1,000,163 → 1,000,121）。

### D-06 一 zip 多坐标（已修复）

原始表 1,000,163 行仅对应 19,015 个邮编前缀，**平均 52.6 行/zip**。直接 JOIN 会使订单行膨胀 52.6 倍。

**处置**：新建派生表 `geolocation_zip`（19,010 行，`zip_code_prefix` 为主键），对每个 zip 取 `AVG(lat)`、`AVG(lng)`、`MIN(city)`、`MIN(state)`、`COUNT(*)`，**过滤坏点后聚合**。后续所有地理分析只 JOIN 该表。

**连带损失**：5 个 zip 因全部坐标均越界而被整体剔除（5/19,015 = 0.026%），下游表现为无坐标。

### D-07 邮编匹配失败（口径规避）

99,441 条 customers 记录中，**279 条（0.28%）**&#8203; 的 `customer_zip_code_prefix` 在 `geolocation_zip` 中找不到匹配。

**处置**：地理相关分析的样本量为 **99,162**（99,441 − 279），报告中需披露该损失。邮编长度校验 `MIN/MAX(CHAR_LENGTH) = 5/5`，已确认前导零完好，匹配失败源于源数据缺邮编而非格式问题。

### D-08 时间戳逻辑倒置（口径规避，不可删除）

| 检查 | 行数 | 占比 |
|---|---:|---:|
| `order_delivered_carrier_date < order_approved_at` | 1,359 | 1.37% |
| `order_delivered_customer_date < order_delivered_carrier_date` | 23 | 0.02% |
| `order_approved_at < order_purchase_timestamp` | 0 | 0% |
| `order_estimated_delivery_date < order_purchase_timestamp` | 0 | 0% |

**成因**：承运商揽收是实时扫描，而"支付审批通过"时间由支付网关异步回传、存在批量补录，因此出现"先揽收、后审批"的真实倒置。这是**业务现实，不是脏数据**。

**处置**：不删除这 1,359 单（删除会引入选择偏差）。计算"审批→揽收"时长时将负值截断为 0，并在报告中单列该比例。

### D-09 关键时间字段缺失（口径规避）

| 字段 | 缺失行数 | 占比 |
|---|---:|---:|
| `order_approved_at` | 160 | 0.16% |
| `order_delivered_carrier_date` | 1,783 | 1.79% |
| `order_delivered_customer_date` | 2,965 | 2.98% |
| `order_estimated_delivery_date` | 0 | 0% |
| 状态=delivered 但无送达时间 | 8 | 0.01% |

由以上推导：有送达时间的订单 96,476 单，其中 6 单状态非 `delivered`（轻微状态滞后）。

**处置**：延迟相关分析的样本定义为 `order_status='delivered' AND order_delivered_customer_date IS NOT NULL`，**n = 96,470**。

### D-10 品类缺失与翻译缺失（已解决）

- `products.product_category_name` 为 NULL：**610 行（1.85%）**&#8203;——源数据未标注品类
- 品类名在 `category_translation` 中无对应翻译：**2 个品类，涉及 13 个商品（0.04%）**&#8203;
  - `portateis_cozinha_e_preparadores_de_alimentos`（10 个商品）
  - `pc_gamer`（3 个商品）

**判定**：两个品类名格式规范、无空格/大小写异常，属**真实缺失**而非脏值，且均为 Olist 数据集已知的翻译表遗漏项。

**处置**：不动原始表（保持审计可复现），在查询层通过映射补全；610 个空品类统一归为 `unknown`。品类覆盖率达到 **98.11%**（商品口径）。


### D-11 支付金额与商品金额口径差（口径规避）

| 指标 | 金额 |
|---|---:|
| `SUM(order_payments.payment_value)` | 16,008,872.12 |
| `SUM(order_items.price + freight_value)` | 15,843,553.24 |
| 差额 | **165,318.88（+1.04%）**&#8203; |

**成因**：voucher/分期付款记录、取消单已收款未退款、运费在两种口径中归属不一致。

**处置**：GMV 类指标须声明口径——**商品/品类分析用 `order_items`，支付/客单分析用 `order_payments`**，两者不可混用。

### D-12 customer_id ≠ 自然人（口径规避）

99,441 个 `customer_id` 对应仅 **96,096 个 `customer_unique_id`**，差额 **3,345（3.36%）**&#8203; 为同一人多账号。

**处置**：复购率、留存、生命周期价值一律使用 `customer_unique_id`；用 `customer_id` 会把复购率系统性低估。

### D-13 order_items JOIN 膨胀（口径规避）

112,650 行 / 98,666 单 = **1.142 行/单**（多商品订单与多卖家订单所致）。

**处置**：任何订单级指标（客单价、运费、延迟）必须先 `GROUP BY order_id` 汇总再计算，否则 `AVG(price)` 得到的是"商品行均价"。

### D-14 首尾月份数据残缺（口径规避）

2016-09~2016-12 仅约 300 单；2018-09~2018-10 数据被截断（2018-10-17 后无记录）。

**处置**：月度趋势、环比、复购窗口分析统一裁剪到 **2017-01-01 ~ 2018-08-31**。

### D-15 review_answer_timestamp 零日期（已修复）

`LOAD DATA` 把非法日期 `0000-00-00 00:00:00` 静默降级为 warning 后入库（Error 1292 的降级形态），全表 **1 行**。

**处置**：`UPDATE ... SET review_answer_timestamp = NULL WHERE CAST(... AS CHAR) = '0000-00-00 00:00:00'`。**不删行**——该行其余字段（评分、订单号）有效。副作用：`ROW_NUMBER() ... ORDER BY review_answer_timestamp DESC` 时该行排最后，符合预期。

### D-16 同日多单污染复购口径（已修复，影响复购率 30%）

2,801 个"复购"客户中，**853 对（30.5%）**&#8203; 的第二单与首单间隔不足 24 小时，**834 对（29.8%）**&#8203; 落在同一日历日。这类"二次购买"是下单拆单、支付失败重试或多卖家分别结算，不是真实复购。

**处置**：复购定义加约束 `gap_to_second >= 1 天`（日历日），复购率由 **2.91% 修正为 2.05%**（1,967/96,096）。
**影响**：修正后"首单延迟 vs 准时"的差异由 −0.80pp 扩大到 **−0.88pp**（z 由 2.57 升至 3.34），说明拆单噪音原本**稀释**了延迟效应。

### D-17 延迟分箱边界开闭不清（已修复）

逐日分箱原写 `WHEN delay_days <= 15 THEN FLOOR(delay_days)`，导致 `(15, 16)` 区间的 **150 单**&#8203; 落入"16~30 天"箱，而"满 15 天"只剩恰好 15.00 的 **9 单**（差评率 66.67%，样本过小、不可用）。

**处置**：改为 `WHEN delay_days < 16 THEN FLOOR(delay_days)`（闭开区间）。修正后：满 15 天 = **159 单 / 78.71%**，16~30 天 = **866 单 / 82.34%**（原 1,016 单 / 81.91%）。
**教训**：凡 `CASE + FLOOR` 分箱，必须用无歧义的 `SUM(条件)` 独立算一遍各段样本量当锚点（见 `03_attribution_delay_bins.sql` §5）。注：该问题**不影响** 16-1b/16-2 的粗分箱（其边界为 `<=15`，语义自洽）。

### D-18 MySQL 除法小数位截断（已规避）

MySQL 的 `div_precision_increment` 默认 4，`1/4263` 返回 **0.0002**（而非 0.00023458）——用于方差/标准误计算会显著低估 SE。实测同一组数据：错误写法 z = **3.78**，正确写法 z = **3.34**。

**处置**：所有涉及样本量倒数的计算统一写 `1e0/n` 或 `CAST(x AS DOUBLE)/n`。见 `04_repurchase.sql` §4。

### D-19 评价时点早于送达 / 文本样本自选偏差（口径规避）

文本分析阶段暴露的两个口径问题，**都不是数据错误，但会直接改变结论的方向**，必须写进方法段：

**① 11.27% 的评价写在送达之前。** 38,902 条"有正文 + 有送达时间"的评价中，4,385 条（11.27%）的 `review_creation_date` 早于 `order_delivered_customer_date`；在"明确说没收到"的 4,270 条中，这一比例高达 **40.42%**。原因是 Olist 的评价问卷在承诺日附近触发，用户可在收货前作答。

> 影响：送达订单的差评里说"没收到"，反映的是**等待焦虑**而非永久丢件。因此判送达只能依据 `order_delivered_customer_date`，不能用评论文本。
> 校验：`sql/05_review_text_checks.sql` §4。

**② 文本覆盖率与评分强相关。** 98,672 条订单级去重评价中，仅 **41.32%** 带正文；1 星用户开口率 76.62%、4 星仅 31.25%。有正文组的差评率 **26.58%**，全样本 14.69%——**文本样本的差评率是整体的 1.8 倍**。

> 影响：文本结论只能用于**组间对比**（如"迟到组的差评更多在骂物流"），不能用于推断整体差评的原因构成。
> 校验：`sql/05_review_text_checks.sql` §1~§3；分类方法见 `scripts/review_mining.py`。
